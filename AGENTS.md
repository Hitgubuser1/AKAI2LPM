# Working on AKAI2LPM

These instructions apply throughout the repository.

## Start here

- Read the [vault index](docs/vault/README.md) and the relevant decision or protocol notes. Inspect git status and the diff before editing. Keep unrelated edits out of your commits.
- The first target is the original APC mini MK1 with Sting VST3 in Ableton Live on Windows. Follow with macOS/AU and Linux/CLAP host validation when setups are available.
- The Python bench tool is in tools/sting_probe.py. Its setup, commands and host acceptance criteria are in the [PoC runbook](docs/vault/sting-poc.md).

## Implementation

- Keep OS MIDI endpoints, controller profiles and shared Sting translation independent. Verify the exact controller generation when citing MIDI addresses.
- Preserve positions, press and release, simultaneous holds and message direction. Leave musical notes generated by Sting on the host's normal routing path.
- Forward controller and LED events as they arrive. Keep UI refresh, log writes and disk I/O off that path. Use a small native UI, event-driven MIDI and standard drawing without requiring a dedicated GPU. Suspend visual refresh with the window hidden.

## Verification

- Run `python -B -m unittest discover -s tests -v` from the repository root for the probe tests, and `git diff --check` before staging. Add focused regression tests when changing protocol behavior.
- Report which automated checks ran. Record host and hardware evidence in the vault with versions, endpoint backend, expected and observed behavior, and traffic direction. Treat Windows, macOS and Linux CI results independently from actual Sting host and APC sessions.
- Before release, measure latency and jitter in both directions under normal and burst traffic. Record package size, installed footprint, RAM, CPU and GPU use. See the [release requirements](docs/vault/decisions.md).

## Git workflow

- For new work, start a short-lived branch based on main, such as `poc/sting-host-matrix` or `feat/controller-profiles`. Follow the [PR and release workflow](docs/vault/README.md#git-workflow).
- Stage explicit paths or hunks at each complete, verified milestone. Inspect `git diff --cached` and run `git diff --cached --check`. Commit each coherent change locally with a Conventional Commit subject that names the actual change, such as `docs(workflow): document agent checks` or `test(midi): cover pad release`.
- Keep local commit identities on the repository's GitHub noreply address. Push and open or merge PRs when the task authorizes publication.
